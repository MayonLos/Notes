## 直觉

C++ 内存管理的核心思想只有一句：**把资源的生命周期绑定到对象的生命周期上。**

这句话为什么有力量？因为 C++ 有一个别的语言没有的保证：**只要对象离开作用域，析构函数一定会被调用**——正常返回会调，中途 `return` 会调，抛异常栈展开时也会调。这是编译器写死的。

于是有了 RAII：**构造时获取资源，析构时释放资源**。你不需要记得释放，因为不释放是不可能的。

```cpp
{
    File f("data.txt");   // 构造：打开
    doSomething();        // 就算这里抛异常
}                         // 析构：一定会关闭
```

对比一下手写 `delete` 的世界：每一条提前返回的路径、每一个可能抛异常的地方，你都得记得释放一次。漏一条就是泄漏。**RAII 把「记得做」变成了「不可能不做」。**

智能指针就是把 RAII 套在堆内存上：`unique_ptr` 的析构函数里调 `delete`，如此而已。它是零开销的——编译后和裸指针一样快。

Move 语义解决的是另一个问题：RAII 对象通常不能拷贝（拷贝一个文件句柄是什么意思？），但**可以转移所有权**。`std::move` 不移动任何数据，它只是把对象标记成「可以被掏空」，让接收方接管资源。被掏空后的源对象处于**有效但未指定**的状态（valid but unspecified）——还能安全析构和重新赋值，但里面剩什么由类型自己规定。

三者是一条线：**RAII 定规则 → 智能指针是实例 → Move 让所有权能流动。**

## 原理与推导

### C++ 内存模型

| 区域 | 分配方式 | 生命周期 |
|:---|:---|:---|
| **栈** | 自动 | 作用域结束即销毁 |
| **堆** | `new/delete`（应交给智能指针） | 显式释放 |
| **静态段** | 编译期 | 整个程序运行期间 |

### RAII 原则

资源在**构造时获取**，在**析构时释放**，异常安全由编译器保证：

```cpp
class File {
    FILE* handle;
public:
    File(const std::string& path) { handle = fopen(path.c_str(), "r"); }
    ~File() { if (handle) fclose(handle); }

    File(const File&) = delete;              // 禁止拷贝：句柄不能有两个主人
    File& operator=(const File&) = delete;
};

{ File f("data.txt"); }   // 离开作用域自动关闭
```

> [!important] RAII 不只管内存
> 文件句柄、互斥锁（`std::lock_guard`）、网络连接、数据库事务——**任何有「获取/释放」配对的资源**都适用。这是 C++ 相对 GC 语言的真正优势：GC 只回收内存，管不了锁和文件。

### 智能指针

**`unique_ptr` — 独占所有权（首选）**

```cpp
auto ptr = std::make_unique<int>(42);   // 推荐 make_unique
auto ptr2 = std::move(ptr);             // 可移动，ptr 变 nullptr
// 离开作用域自动释放，零额外开销
```

**`shared_ptr` — 共享所有权（引用计数）**

```cpp
auto p1 = std::make_shared<int>(42);
auto p2 = p1;               // 引用计数 = 2
std::cout << p1.use_count();
// 最后一个 shared_ptr 销毁时释放
```

**`weak_ptr` — 弱引用（打破循环）**

```cpp
class Node {
public:
    std::shared_ptr<Node> next;
    std::weak_ptr<Node>   prev;   // 不增加引用计数
};
```

| | 所有权 | 开销 | 用在哪 |
|:---|:---|:---|:---|
| `unique_ptr` | 独占 | **零** | 默认选择 |
| `shared_ptr` | 共享 | 引用计数（原子操作）| 确实需要多个主人时 |
| `weak_ptr` | 无 | 小 | 打破循环、观察者 |

### Move 语义（C++11）

```cpp
class MyVec {
    int* data; int size;
public:
    MyVec(MyVec&& other) noexcept              // 移动构造：接管资源
        : data(other.data), size(other.size) {
        other.data = nullptr; other.size = 0;  // 必须把源置空
    }
};

std::string s = "hello";
vec.push_back(std::move(s));   // 移动而非拷贝；s 之后「有效但未指定」，别再读它的值
```

> [!important] `std::move` 不移动任何东西
> 它只是一个类型转换，把左值转成右值引用，**告诉编译器「这个对象我不要了，可以掏空」**。真正的转移发生在移动构造/移动赋值函数里。

### 现代 C++ 特性

```cpp
auto x = 42;                    // 类型推导
auto it = vec.begin();

auto add = [](int a, int b) { return a + b; };      // Lambda
int mult = 3;
auto multiply = [mult](int x) { return x * mult; }; // 值捕获

constexpr int factorial(int n) {                     // 编译期计算
    return n <= 1 ? 1 : n * factorial(n - 1);
}
constexpr int f5 = factorial(5);   // 编译期就得到 120
```

### 最佳实践

| 原则 | 说明 |
|:---|:---|
| 默认用 `unique_ptr` | 独占所有权，零开销；需要共享时才升级 |
| 用 `make_unique`/`make_shared` | 避免裸 `new`，异常安全，`make_shared` 还少一次分配 |
| 遵循 RAII | 资源释放写在析构函数里 |
| 大对象用 Move | `std::move` 避免深拷贝 |
| **不写裸 `new/delete`** | 现代 C++ 里几乎没有正当理由 |

## 例题

### 例 1 · 手写 `delete` 为什么会漏

```cpp
void process() {
    int* data = new int[1000];
    if (!check()) return;       // ← 这里漏了 delete[]
    if (risky()) throw Error{}; // ← 这里也漏了
    delete[] data;              // 只有走到这里才释放
}
```

每加一条提前退出的路径，就多一处要记得释放。改成 RAII：

```cpp
void process() {
    auto data = std::make_unique<int[]>(1000);
    if (!check()) return;        // 自动释放
    if (risky()) throw Error{};  // 栈展开时自动释放
}                                // 正常结束也自动释放
```

**三条路径，一份代码。**

### 例 2 · 循环引用导致的泄漏

```cpp
struct Node { std::shared_ptr<Node> next, prev; };

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;    // b 的计数 = 2
b->prev = a;    // a 的计数 = 2
// 出作用域后各减 1 → 都还是 1 → 永远不释放
```

把其中一个方向改成 `weak_ptr`（通常是「回指」的那个）：

```cpp
struct Node { std::shared_ptr<Node> next; std::weak_ptr<Node> prev; };
```

**判据**：所有权是单向的，`shared_ptr` 顺着所有权方向，反向一律 `weak_ptr`。

### 例 3 · Move 让容器扩容不再昂贵

```cpp
std::vector<std::string> v;
v.push_back(std::string(1000, 'x'));   // 临时对象是右值 → 移动，不拷贝
```

`vector` 扩容时要把旧元素搬到新内存。有移动构造函数（且标了 `noexcept`）时，搬运是**指针转移**而非逐字节深拷贝。

> [!important] 移动构造一定要写 `noexcept`
> 不写的话，`vector` 扩容为了保证异常安全会**退回用拷贝**，移动语义白写了。

## 易错点

> [!warning] 循环引用导致内存泄漏
> 两个 `shared_ptr` 互相持有，引用计数永远不为 0。见例 2。用 `weak_ptr` 打破。

> [!warning] `new`/`delete` 不匹配
> `new` 配 `delete`，`new[]` 配 `delete[]`，混用是 UB。**现代 C++ 应完全避免裸 `new/delete`**，这条错误就不存在了。

> [!warning] 用同一个裸指针构造两个 `shared_ptr`
> ```cpp
> int* raw = new int(42);
> std::shared_ptr<int> a(raw);
> std::shared_ptr<int> b(raw);   // 两个独立的控制块 → 双重释放
> ```
> 永远用 `make_shared`，别从裸指针二次构造。

> [!warning] `std::move` 之后还用原对象
> 被移动的对象处于「有效但未指定」状态。可以给它赋新值、可以析构，但**读它的内容是没有意义的**。`std::move(s)` 之后 `s` 通常为空。

> [!warning] 到处用 `shared_ptr`
> 引用计数是原子操作，多线程下有真实开销，而且共享所有权让生命周期变得难以推理。**默认 `unique_ptr`，确实需要多个主人时才用 `shared_ptr`。**

> [!warning] Lambda 悬垂捕获
> ```cpp
> auto f = [&]() { return localVar; };   // 引用捕获
> return f;                              // localVar 已销毁 → 悬垂
> ```
> 要活得比当前作用域长的 Lambda，用**值捕获**或捕获智能指针。

> [!warning] 忘记 `noexcept`
> 移动构造/移动赋值不标 `noexcept`，标准库容器会为了强异常安全保证而改用拷贝。见例 3。
